# Locatediscount

Locatediscount connects consumers with local business offers. Consumers use it free of charge. A business is charged a platform fee only when it validates a customer's one-time code in-store.

## Roles

| Role | Main job | Fee visibility |
| --- | --- | --- |
| Customer | Browse offers without a login, then creates a lightweight profile on the first code claim. | Never sees or pays the business fee. |
| Business | Fund wallet, publish offers, redeem codes. | Sees fee and wallet movement in real time. |
| Admin | Approve funding, set fees, audit and correct records. | Sees the complete platform ledger. |

## Local setup

```bash
cd "/Users/user/Desktop/Located Discount"
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
python3 -m flask --app app init-db
python3 -m flask --app app create-admin
python3 -m flask --app app run --debug
```

Open `http://127.0.0.1:5000`. The CLI command creates the primary admin; that administrator can create and manage sub-admins from `/admin/team`. Only business registration is public; visitors never need to register to claim a deal. An administrator must approve each new business at `/admin/businesses` before it can publish, accept wallet funding, add products, or validate a code.

To run locally against Neon too, make sure the `DATABASE_URL=postgresql://...` line in `.env` is uncommented. Leave it commented only when you intentionally want the local SQLite fallback.

## Deploy to Render

This repository includes `render.yaml` for a production web service backed by Neon Postgres. On startup, the app reads `DATABASE_URL`, connects over SSL, and creates its application tables and default categories if they do not already exist.

1. Push this project to its **own** GitHub repository. The current Git remote points to an unrelated repository, so do not use it for this deployment.
2. In Render, select **New > Blueprint**, connect the GitHub repository, and select the branch containing `render.yaml`.
3. In the service's **Environment** page, set `DATABASE_URL` to the complete connection string already in your local `.env`. Use the Neon connection string exactly as supplied, including its `sslmode=require` option. It is a secret: do not commit it or add it to `render.yaml`.
4. Add the remaining production settings from `.env`: `PAYSTACK_SECRET_KEY` (or `PAYSTACK_TEST_SECRET` while testing), `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_SECRET_KEY`. Add a `MAIL_FROM` and the SMTP settings if password-reset email is enabled.
5. Create the service. The initial deploy creates the schema in Neon. From the Render Shell, run `flask --app app create-admin` once to create the first administrator.
6. Copy the Render URL into `PAYSTACK_CALLBACK_URL` and set Paystack's webhook to `https://<your-render-domain>/payments/paystack/webhook`. After a custom domain is connected, update the callback URL to use that domain.

`SECRET_KEY` is generated by Render, and `FLASK_ENV=production` plus secure session cookies are configured automatically. Render supplies the listening port to Gunicorn. No Render persistent disk is needed: Neon stores users, wallets, codes, and ledgers independently of Render deploys and restarts.

## Paystack wallet funding

Set the server-side secret in `.env` (the existing `PAYSTACK_TEST_SECRET` name is supported for testing; use `PAYSTACK_SECRET_KEY` in production):

```bash
PAYSTACK_SECRET_KEY="sk_live_..."
PAYSTACK_CALLBACK_URL="https://your-domain.example/payments/paystack/callback"
```

In the Paystack dashboard, set the webhook URL to:

```text
https://your-domain.example/payments/paystack/webhook
```

The secret key is used only by the server. A business starts checkout from its wallet page; the app records a pending local reference, initializes Paystack in kobo, and redirects to Paystack’s hosted HTTPS checkout. The signed `charge.success` webhook is the primary fulfilment path, while the callback verifies the transaction through Paystack for immediate browser feedback. Both paths validate the reference, successful status, exact amount, and NGN currency, and use the same idempotent database transaction so a retry cannot credit the wallet twice.

## Cloudinary product media

New product images are stored in Cloudinary. Configure the server-only credentials in `.env`:

```bash
CLOUDINARY_CLOUD_NAME="your-cloud-name"
CLOUDINARY_API_KEY="your-api-key"
CLOUDINARY_SECRET_KEY="your-api-secret"
```

`CLOUDINARY_API_SECRET` is also supported as an alternative name for the secret. The browser never receives either credential. Images are validated as JPEG, PNG, or WebP and limited to 5 MB before upload. The database stores Cloudinary's HTTPS delivery URL and public ID; if the related product database write fails, the newly uploaded assets are removed from Cloudinary. Existing images saved by older versions continue to load from local storage.

## Password reset email

Forgot-password links are single-use and expire after 30 minutes. Configure SMTP in production:

```bash
export SMTP_HOST="smtp.example.com"
export SMTP_PORT="587"
export SMTP_USERNAME="smtp-user"
export SMTP_PASSWORD="smtp-password"
export SMTP_USE_TLS="1"
export MAIL_FROM="no-reply@example.com"
```

The public response is intentionally identical whether or not an email address exists. If SMTP is not configured, the application does not expose the reset link in the browser.

## Demo catalogue


## Full User Journey

### Business: account to live deal

1. The merchant selects **Business** during registration and supplies owner name, email, phone, password, business name, category, address, and city.
2. The server validates the fields before creating a user and a linked business record. Passwords require at least 12 characters containing letters and numbers, then are stored only as salted hashes.
3. The new business starts in a pending-review state with a `₦0` wallet and `₦2,000` default low-balance threshold. An admin must approve it before operational actions are available.
4. In **Wallet**, the merchant can pay through Paystack for automatic verified credit, or submit a manual bank-transfer reference for administrator review.
5. A successful Paystack confirmation credits the wallet exactly once. Manual transfers remain pending until an administrator approves them.
6. The merchant clicks **Create deal**, enters the title, description, category, terms, future expiry, and redemption limit. The page forecasts cost using the current fee, for example `₦150 x 50 = ₦7,500`.
7. The server publishes an active deal only if all validation checks pass. A deal closes automatically when it expires or reaches its redemption limit.

### Customer: discover to code, no password signup required

1. A customer searches by business/deal name, category, city, or area. Opening an offer displays its business, directions, terms, and expiry.
2. When **Get a one-time code** is selected, the server verifies the deal is active, unexpired, and has remaining redemptions. No password, email, or payment is requested.
3. On the first claim only, the customer provides a name and phone number. The app creates a lightweight non-login profile plus a persistent browser/device token. This makes **My codes** available with active, redeemed, and expired code history.
4. A device may hold only one active code for a particular business, even when that business has multiple live deals. The customer must redeem or let that code expire before claiming another code from the same vendor.
5. The server creates a random `LD-XXXXXXXX` code using the `secrets` cryptographic generator. The code expires after seven days or the deal expiry, whichever comes first; its QR SVG is generated locally.
6. The code belongs to the deal's business. A different business cannot validate it because redemption checks the owning business before changing any state.
7. The customer shows the code to that business after receiving the discount. The customer never sees or pays a platform fee.

### Vendor and product discovery

- `/vendors` lists only approved, unblocked businesses and supports vendor/category plus city/area search.
- `/products` lists public products from those same vendors and supports product/vendor plus city/area search.
- Businesses add catalogue entries at `/business/products`. Each new product can include up to five JPEG, PNG, or WebP images. Images are checked by file signature, limited to 5 MB each, assigned random Cloudinary public IDs, and delivered through stored HTTPS URLs. Product links must use HTTPS; prices are parsed with exact decimal arithmetic.
- A product detail page shows its image gallery, description, price, business address, vendor page, and the active offers that can generate a code for that vendor. It also explains that the discount must be applied before the business validates the one-time code.

### Business: redemption and automatic billing

Staff should redeem only after applying the promised discount.

1. Staff sign in to the relevant business and open **Redeem a customer code**.
2. They type the `LD-XXXXXXXX` value. A future QR scanner can populate this same field; server validation remains identical.
3. The server validates the format, finds the code, and checks it belongs to that business, is active, is unexpired, and is attached to a live deal. It also checks that the business is not already blocked for a top-up.
4. If a check fails, the system makes no financial or code change and returns an error.
5. If valid, one database transaction performs all of the following together:
   - Marks the code `redeemed`, with the time and staff user.
- Reads the applicable business-specific fee, or the admin-controlled default when no override exists.
   - Debits the business wallet.
   - Increments the deal redemption count and closes it at its limit.
   - Writes a posted wallet transaction.
   - Writes one immutable ledger entry with business, deal, code, fee, resulting balance, and time.
6. The staff screen immediately shows the exact fee deducted and new balance. The admin master ledger receives the same entry.

The code update is conditional and the ledger has a unique code reference. Two near-simultaneous attempts cannot successfully redeem and bill the same code twice.

### Low-balance behavior

The current customer is honoured, but future redemptions stop when the resulting wallet balance is below the business threshold.

For example, with `₦100` in the wallet and a `₦150` fee, the current valid redemption succeeds, resulting in `-₦50`. The business is marked `needs_top_up`; the next code is blocked. Once a submitted top-up is approved, the flag clears and redemption resumes.

### Admin: operations and disputes

The admin panel can:

- Review the master ledger of all completed redemptions.
- Review and approve verified pending top-ups.
- View business balances and low-balance status.
- Approve pending businesses, block a business immediately, restore access, and set a business-specific future redemption fee at `/admin/businesses`.
- Change the default redemption fee. The new rate applies only to future redemptions; historical ledger fees remain unchanged. The backend also supports a business-specific override for plan/category pricing.
- Credit or debit a wallet for a dispute. A 5 to 250 character reason is required, and every adjustment creates both a wallet transaction and an admin audit record.
- Add or archive marketplace categories, create and deactivate sub-admins, review paginated audit logs, and inspect platform analytics.

Businesses have a separate analytics workspace with claim volume, verified redemptions, conversion rate, fees, daily activity, and deal-level performance.

For disputes, preserve the original redemption entry. Use a documented wallet adjustment rather than deleting financial history.

## Data States

| Record | States | Transition |
| --- | --- | --- |
| Code | `active`, `redeemed`, `expired` | Claim creates active; successful validation redeems it; expiry is enforced at validation. |
| Deal | active or closed | Expiry or redemption limit closes it. |
| Top-up | `pending`, `approved`, `rejected`, `posted` | Merchant submits pending; admin approval credits it. Redemptions and adjustments are posted immediately. |
| Wallet | normal or `needs_top_up` | A below-threshold redemption sets the flag; approved funding clears it. |

## Security Controls

- Salted password hashing; plaintext passwords are never stored.
- Role-based authorization: business and admin areas are protected; new businesses require explicit admin approval; customer code views are restricted to the browser session/profile that claimed them.
- Device tokens are stored only as SHA-256 hashes in the database. A device can retain one active code per vendor at a time.
- CSRF token required for every POST, checked with constant-time comparison.
- HTTP-only, SameSite session cookies, private-page no-store caching, CSP, frame protection, MIME-sniffing protection, referrer policy, and HSTS when HTTPS secure cookies are enabled.
- Five failed attempts for an IP/email combination produces a 15-minute sign-in block. The stored limiter key is SHA-256 hashed.
- Password recovery uses SHA-256-hashed, single-use reset tokens with a 30-minute expiry. Successful password changes invalidate outstanding reset links and sign the user out.
- Server-side validation for email, phone, password, business/deal fields, code, wallet amount, references, admin fee, and wallet adjustments.
- Cryptographically random codes and references. Atomic transaction writes ensure status, balance, wallet history, and ledger cannot diverge.
- QR SVGs are generated locally; code data is never sent to a third-party QR provider.
- Product uploads accept only JPEG, PNG, and WebP signatures. Client file extensions are ignored, Cloudinary public IDs are random, and failed database writes remove newly uploaded assets.

## Verification

Run the complete, isolated workflow test suite with:

```bash
python3 -m unittest discover -s tests -v
```

The tests cover business registration, deal creation, manual top-up submission and approval, first-claim customer profile creation, QR code generation, persistent My Codes access, vendor-only redemption, duplicate-redemption prevention, wallet/ledger consistency, admin categories, sub-admins, audit logs, analytics, password recovery, and CSRF enforcement.

## Production Checklist

This is a secure pilot build. Before public launch:

- Set a long random `SECRET_KEY`, set `SESSION_COOKIE_SECURE=1`, and use HTTPS only.
- Use Gunicorn behind a reverse proxy, not Flask debug mode.
- Back up Neon and use versioned migrations before making future production schema changes.
- Configure the live Paystack secret, HTTPS callback URL, and signed webhook URL; complete Paystack’s live-mode account checks before accepting production payments.
- Configure the Cloudinary cloud name, API key, and API secret as server-side environment values and restrict access to the production environment.
- Add email/phone verification, Redis-backed rate limiting, admin 2FA, monitoring, backups, and incident response.
- Enforce phone OTP verification before allowing profile recovery on a new device. Browser cookies can be cleared, so this verification or a native-app device attestation is required for a strict cross-device anti-abuse guarantee.

## Project Layout
